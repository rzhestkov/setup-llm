# Roadmap: большой контекст без немедленного падения производительности

## Цель

Обеспечить работу `llama-server` с контекстом 30–32 тысячи токенов на GPU с ограниченной VRAM без падения скорости уже на коротком первом запросе.

Основная проверяемая гипотеза: при большом `CtxSize` KV-кэш `f16` заранее занимает слишком много VRAM. В результате суммарный расход памяти модели, KV-кэша и вычислительных буферов превышает физически доступную VRAM, после чего Windows/CUDA начинает переносить данные через общую память.

## Ограничения

- Изменения разрабатываются только в отдельной экспериментальной ветке, не в `main`.
- Не обращаться к Git remote без прямого запроса пользователя.
- Не выполнять `git fetch`, `git pull`, `git push`, `git remote`, `gh`, команды Gitea и создание PR без отдельного разрешения.
- Количество веток, публикацию веток и PR контролирует пользователь.
- До начала реализации сохранить совместимость с существующими `portablellm.ini`.
- Не считать успешную загрузку модели достаточной проверкой: необходимо измерять память и скорость генерации.

## Исходное состояние

Для тестовой модели Gemma 4 31B IQ3_XS и `CtxSize=16000` в журнале зафиксировано:

```text
CUDA0 model buffer   ≈ 12452 MiB
CUDA0 KV buffer      ≈  2460 MiB
CUDA0 compute buffer ≈   523 MiB
Итого                ≈ 15435 MiB
Доступно             ≈ 15223 MiB
```

Уже при 16 тысячах контекста отсутствует безопасный запас VRAM. Увеличение `CtxSize` до 30 тысяч с KV-кэшем `f16` дополнительно увеличивает расход памяти примерно на 1,1 ГиБ.

`FitTargetMiB=2048` сейчас не обеспечивает заявленный запас: проект явно передаёт одновременно `GpuLayers=all` и `CtxSize`, поэтому `--fit` не может изменить эти параметры.

## Этап 0. Зафиксировать базовые измерения

До изменения кода провести одинаковый короткий тест при:

- `CtxSize=16000`;
- `CtxSize=18000`;
- `CtxSize=24000`;
- `CtxSize=30000`.

Для каждого запуска записать:

- используемую модель и её размер;
- параметры запуска `llama-server`;
- свободную VRAM перед загрузкой;
- размеры model/KV/compute buffers;
- количество выгруженных на GPU слоёв;
- скорость обработки промпта в tokens/s;
- скорость генерации в tokens/s;
- фактическую длину промпта;
- наличие использования shared GPU memory в Windows;
- результат короткого контрольного ответа.

Для сравнения с LM Studio использовать ту же модель, тот же GGUF-файл, одинаковый контекст и по возможности одинаковые типы K/V-кэша.

## Этап 1. Добавить параметры типа KV-кэша

Добавить в `portablellm.ini`:

```ini
CacheTypeK=f16
CacheTypeV=f16
```

Передавать их в `llama-server`:

```text
--cache-type-k <CacheTypeK>
--cache-type-v <CacheTypeV>
```

Требования к реализации:

- старый конфиг без новых ключей должен продолжить работать;
- на первом экспериментальном этапе значение по умолчанию оставить `f16/f16`, чтобы не менять поведение существующих установок молча;
- записывать выбранные типы K/V в `startup.log`;
- рекомендованный экспериментальный профиль — одинаковые `q8_0/q8_0`;
- `q4_0/q4_0` тестировать отдельно как более экономичный, но потенциально менее точный вариант;
- не использовать смешанные типы K/V без отдельного измерения производительности Flash Attention.

## Этап 2. Добавить быстрый перезапуск с конфигурацией-переопределением

Сохранить существующее назначение основных скриптов:

- `Start-PortableLLM` полностью запускает систему и читает безопасные проверенные настройки из `portablellm.ini`;
- `Stop-PortableLLM` полностью останавливает систему;
- новый `Restart-PortableLLM` оставляет Open WebUI работающим, останавливает только `llama-server`, ждёт освобождения памяти, повторяет обычный выбор модели, оценивает VRAM и запускает сервер с effective-конфигурацией.

Добавить файл:

```text
config\restartllm.ini
```

Он содержит только параметры, которые пользователь хочет временно переопределить для очередного перезапуска. Файл может быть пустым и может вообще не содержать параметров.

Перед каждым перезапуском заново формировать:

```text
temp\portablellm_tmp.ini
```

Правило объединения:

```text
portablellm_tmp.ini = portablellm.ini + restartllm.ini
```

Если ключ присутствует в `restartllm.ini`, его значение заменяет значение из `portablellm.ini`. Если ключ отсутствует, используется базовое значение. Итог всегда строится заново из `portablellm.ini`, а не из предыдущего `portablellm_tmp.ini`, поэтому эксперименты не накапливаются между перезапусками.

Пример:

```ini
; portablellm.ini
CtxSize=19000
BatchSize=2048
UBatchSize=512
CacheTypeK=f16
CacheTypeV=f16
```

```ini
; restartllm.ini
CtxSize=30000
```

В `portablellm_tmp.ini` должны оказаться `CtxSize=30000` и все остальные значения из базового файла.

Если `restartllm.ini` пуст, `portablellm_tmp.ini` должен совпасть по эффективным параметрам с `portablellm.ini`, а модель просто перезапускается с безопасной базовой конфигурацией.

### Универсальность overlay

Технически через `restartllm.ini` разрешено переопределять любые параметры без whitelist, запретов и специальных ограничений. Механизм объединения не должен проверять допустимость имени или значения параметра и не должен блокировать перезапуск на основании собственных правил. Дальнейшее поведение определяется существующей логикой запуска и самим `llama-server`.

Рекомендации о том, какие параметры обычно относятся к модели, а какие требуют полного перезапуска системы, оставить только в комментариях внутри шаблона `restartllm.ini` и в документации. Эти комментарии не должны превращаться в программные проверки.

Параметры работающего Open WebUI, Python, путей или портов могут быть переопределены в итоговом файле на общих основаниях, но при перезапуске только `llama-server` уже работающие компоненты не перечитывают свои настройки. Это пояснить комментариями, не запрещая такие переопределения.

### Диагностический вывод

Перед перезапуском показать и записать в `logs\restart.log` точную разницу между базовой и временной конфигурацией:

```text
Параметр    portablellm.ini    restartllm.ini / итог
CtxSize     19000              30000
```

Если переопределений нет, вывести:

```text
restartllm.ini не содержит переопределений.
Используется базовая конфигурация portablellm.ini.
```

Если ключ явно указан с пустым значением, это считается переопределением пустым значением, а не отсутствующим параметром.

Для воспроизводимости сохранять в `restart.log`:

- время перезапуска;
- путь активной модели;
- список переопределённых параметров со старыми и новыми значениями;
- путь к сформированному `portablellm_tmp.ini`;
- итоговую командную строку `llama-server`;
- PID старого и нового процесса;
- результат запуска.

Обычный `Start-PortableLLM` не должен читать `restartllm.ini` или `portablellm_tmp.ini`: полный запуск всегда возвращает систему к базовой конфигурации.

### Выбор модели при перезапуске

После остановки прежнего `llama-server` и паузы для освобождения памяти новый restart-скрипт выполняет тот же интерактивный выбор модели, что и обычный Start. Можно выбрать прежнюю или другую GGUF-модель из эффективного `ModelsDir`. После выбора выполняется оценка VRAM и запускается новый экземпляр сервера. Путь предыдущей модели не фиксирует выбор автоматически.

## Этап 3. Проверить профиль большого контекста

Первый экспериментальный профиль:

```ini
GpuLayers=all
FlashAttention=on
CtxSize=30000
CacheTypeK=q8_0
CacheTypeV=q8_0
BatchSize=512
UBatchSize=256
ParallelSlots=1
PromptCacheMiB=0
```

Затем проверить `CtxSize=32768`.

Ожидаемый эффект: KV-кэш `q8_0/q8_0` должен занимать приблизительно вдвое меньше памяти, чем `f16/f16`, позволяя оставить все слои модели на GPU.

## Этап 4. Добавить контроль запаса VRAM

Предварительная проверка проекта сейчас учитывает в основном размер GGUF-файла и общий резерв. Она не гарантирует, что после создания контекста поместятся KV-кэш и compute buffer.

Необходимо добавить проверку полного бюджета:

```text
model buffer + KV buffers + compute buffers + safety margin <= free VRAM
```

Предварительный ориентир для `safety margin`:

- минимум для эксперимента: 512 MiB;
- предпочтительно: 768–1024 MiB;
- точное значение определить измерениями на тестовой Windows-системе.

Основной вариант реализации — штатный `llama-fit-params.exe --fit-print on` из поставки `llama.cpp`. Он должен получать те же параметры модели, контекста, KV-кэша, batch/ubatch и GPU-offload и возвращать отдельные оценки model/context/compute. Если утилита отсутствует или её вывод не удалось прочитать, использовать прежнюю грубую оценку размера GGUF и резерва как fallback.

Если расчёт превышает безопасный бюджет, скрипт должен до начала работы сообщить:

- сколько VRAM доступно;
- сколько требуется модели;
- сколько требуется KV-кэшу;
- сколько требуется compute buffer;
- какой запас останется;
- какие параметры можно изменить.

Оценка является диагностической: выводить статусы `safe`, `low VRAM margin` и `oversubscribed`, но не запрещать запуск.

## Этап 5. Сделать `--fit` предсказуемым

Добавить специальное значение:

```ini
GpuLayers=auto
```

При `auto` не передавать `--gpu-layers`, чтобы `--fit` мог самостоятельно подобрать offload. При `GpuLayers=all` или числовом значении сохранить полный ручной контроль.

Отдельно документировать:

- явно заданный `CtxSize` не будет автоматически уменьшен;
- автоматическое уменьшение GPU-offload может сохранить устойчивость, но снизить скорость генерации;
- для профиля `q8_0/q8_0` предпочтительно сначала пытаться сохранить `GpuLayers=all`.

## Этап 6. Автоматическая проверка после запуска

После загрузки модели:

- убедиться, что процесс жив;
- дождаться завершения прогрева;
- проверить `/health` или эквивалентную конечную точку сервера;
- выполнить короткий тестовый запрос;
- записать скорость и ошибки CUDA;
- проверить, что ожидаемое количество слоёв осталось на GPU;
- вывести итоговый статус: `safe`, `low VRAM margin` или `unsafe/oversubscribed`.

Не полагаться только на критерий «сервер открыл порт»: при переполнении VRAM он может продолжать работать, но перейти в резко более медленный режим.

## Этап 7. Матрица тестирования

Минимальная матрица:

| Контекст | K/V       | Batch/UBatch | GPU layers        | Назначение                    |
| --------:| --------- | ------------ | ----------------- | ----------------------------- |
| 16000    | f16/f16   | 2048/512     | all               | исходная точка                |
| 30000    | f16/f16   | 512/256      | all               | воспроизведение замедления    |
| 30000    | q8_0/q8_0 | 512/256      | all               | основной кандидат             |
| 32768    | q8_0/q8_0 | 512/256      | all               | целевой максимум              |
| 32768    | q4_0/q4_0 | 512/256      | all               | резервный экономичный профиль |
| 30000    | f16/f16   | 512/256      | подобранное число | сравнение с CPU-offload       |

Каждый тест повторить не менее трёх раз после холодного запуска сервера.

## Критерии успешности

Изменение считается успешным, если:

- при `CtxSize=30000` или `32768` все слои модели остаются на GPU;
- shared GPU memory не начинает заметно расти во время короткого запроса;
- после загрузки остаётся согласованный безопасный запас VRAM;
- скорость короткой генерации отличается от профиля 16–18k не более чем на 10–15%;
- длинный промпт обрабатывается без CUDA OOM и без резкого перехода на CPU;
- контрольные ответы `q8_0/q8_0` остаются приемлемыми по качеству;
- старый конфиг без новых параметров продолжает запускаться;
- в журналах достаточно данных для диагностики без наблюдения только за падением процесса.

## Предлагаемый локальный Git-процесс

Рабочий вариант взаимодействия:

1. Пользователь сообщает, что можно начинать эксперимент.
2. Либо пользователь сам создаёт и переключает ветку, либо просит Codex сделать это локально.
3. Codex проверяет текущую ветку и чистоту рабочего дерева.
4. Codex вносит изменения, выполняет доступные локальные проверки и показывает diff.
5. Пользователь запускает аппаратные тесты на целевой portable-установке и передаёт журналы.
6. Codex корректирует ту же экспериментальную ветку.
7. Коммиты выполняются только по договорённости; публикацию ветки и PR контролирует пользователь.

Рекомендуемое имя первой экспериментальной ветки:

```text
codex/kv-cache-experiment
```

Codex умеет самостоятельно создать локальную ветку командой `git switch -c`, но не должен делать это без явного указания пользователя. Создание локальной ветки не требует Git remote и не вызывает авторизацию в Gitea.

## Git remote

До отдельного прямого запроса пользователя запрещены любые сетевые Git-операции и обращения к Gitea. Для работы достаточно локальных команд:

```text
git status
git branch --show-current
git switch
git diff
git add
git commit
```

Даже чтение сведений через команды, явно обращающиеся к remote, не требуется для выполнения этого roadmap.
